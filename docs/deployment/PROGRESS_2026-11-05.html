تقرير تقدم أعمال DevOps

تاريخ الأعمال: 5 نوفمبر 2026 آخر تحديث: 7 نوفمبر 2026 المسؤول: مصطفى — مسؤول DevOps

يوثق هذا التقرير الأعمال المنجزة، والاختبارات التي نجحت، والمهام المتبقية. ويستند إلى خطة الفريق ووثيقة تسليم المهام، مع التمييز بينهما وبين المتطلبات الرسمية لمشروع التخرج، الإصدار 21.2.

1. الوضع الحالي

أصبح backend يعمل محلياً من production Docker image، خلف Nginx reverse proxy باستخدام HTTPS. وتُنفَّذ database migrations قبل بدء التطبيق. كما تبقى بيانات database وuploaded files محفوظة عند إعادة إنشاء containers.

نجحت اختبارات restart بعد التعطل، وbackup، وrestore في بيئة isolated. وبذلك اكتملت قاعدة التشغيل المحلية للـbackend، بينما لا يزال تشغيل التطبيق الكامل وبعض مهام monitoring وautomation قيد الإنجاز.

2. القرارات والحدود المتفق عليها

  • يستمر العمل محلياً باستخدام العنوان https://localhost.
  • لا يشترط الموضوع الرسمي شراء domain name، أو استئجار VPS، أو نشر public staging. كما لا ينص على أن التشغيل يجب أن يكون محلياً حصراً.
  • تظل public staging جزءاً اختيارياً من خطة الفريق، وليست عائقاً أمام استكمال العمل المحلي.
  • يجب استخدام HTTPS/TLS للاتصالات الخارجية مع backend. ويجوز أن يبقى الاتصال الداخلي بين containers دون encryption.
  • تُحافَظ على architecture الحالية: modular monolith. ولا يعني تعدد containers اعتماد architecture microservices.
  • لن تُجرى تغييرات أخرى في backend code. وأي احتياج يتعلق بـmetrics أو إعدادات CORS أو readiness check يُنسَّق مع المسؤول عنه.
  • أُلغي تعديل health check الذي كان يستعلم عن database، وأُزيل اختباره. لذلك لا يزال المسار /health يشير إلى أن التطبيق يعمل فقط.
  • بقيت تغييرات إعداد migrations وأمر تشغيلها في production، التي تمت الموافقة عليها سابقاً.
  • يُنفَّذ CI/CD في نهاية الخطة، بعد استقرار الإجراءات اليدوية.

3. الأعمال المنجزة

3.1. قراءة الوثائق وفحص المشروع

لماذا احتجناها؟ لتجنب إعادة إنجاز إعداد يعمل، أو إضافة بنية خارجية غير مطلوبة. ومن أمثلتها توضيح أن public staging ليست شرطاً في الموضوع الرسمي المرفق.

تمت مراجعة الوثائق الثلاث التالية، ثم مقارنة محتواها بملفات المشروع الفعلية:

  • en.subject.pdf: المتطلبات الرسمية ومعايير التقييم.
  • devops.pdf: خطة مراحل DevOps.
  • mustapha_work.pdf: الأعمال السابقة والمسؤوليات المتبقية.

تأكدنا من وجود التقنيات التالية: NestJS وTypeORM وMySQL 8.4 وSocket.IO، إضافة إلى إعداد development Compose الذي يضم services database وmigrations وbackend.

كانت development environment وmigrations الأولية تعملان بالفعل؛ لذلك انطلقنا من الإعداد الموجود بدلاً من إعادة بنائه.

3.2. إعداد production image

ما دور Dockerfile؟ هو وصف لطريقة إعداد Docker image: ما نسخة Node.js المستخدمة، وما dependencies المطلوب تثبيتها، وكيف يُبنى code، وما الأمر الذي يبدأ التشغيل. أما image فهي النتيجة المبنية، وcontainer هو نسخة تعمل منها.

لماذا ملف مستقل عن Dockerfile.dev؟ في development نحتاج watch mode لإعادة التشغيل عند تعديل code. أما في production فنحتاج تشغيل النسخة المبنية بصورة مستقرة، دون أدوات التطوير أو الاعتماد على ملفات الجهاز.

الجزء دوره في الإعداد الذي أنجزناه
build stage تثبيت dependencies وتشغيل npm run build لإنتاج ملفات JavaScript داخل dist
npm ci تثبيت الإصدارات المحددة في package-lock.json بصورة قابلة للتكرار
npm prune --omit=dev إزالة devDependencies بعد اكتمال build
runtime stage الاحتفاظ بالتطبيق المبني وdependencies اللازمة للتشغيل
USER node تشغيل التطبيق دون root permissions لتقليل الصلاحيات
EXPOSE 3000 توثيق port الذي يستخدمه التطبيق؛ لا يفتح هذا port على الجهاز
CMD تحديد الأمر الافتراضي الذي يبدأ التطبيق: تشغيل dist/main.js

مثال: نأخذ image نفسها إلى جهاز آخر، فنشغّل التطبيق ببيئة Node.js وdependencies الموجودة داخلها. وتبقى environment variables وvolumes إعدادات منفصلة نمررها عند التشغيل.

أُنشئ ملف بناء production image:

apps/backend/Dockerfile

يتكون البناء من مرحلتين:

  1. تثبيت dependencies، وترجمة code إلى ملفات قابلة للتشغيل، ثم إزالة devDependencies.
  2. نسخ التطبيق المبني وproduction dependencies إلى runtime image.

يعمل backend بالمستخدم node، دون watch mode، ودون ربط source code من الجهاز. كما أُعد مجلد قابل للكتابة لحفظ uploaded files.

نتيجة التحقق: نجح بناء production image. وأبلغ فحص dependencies عن 36 مشكلة أمنية في التثبيت الكامل، و6 بعد إزالة devDependencies. لم تُراجَع هذه النتائج تفصيلياً ولم تُعالَج بعد.

3.3. تهيئة database migrations للـproduction

ما دور migrations؟ تطبيق تغييرات منظمة على database schema، مثل إنشاء table أو إضافة column. يتابع TypeORM ما نُفذ منها في typeorm_migrations ويطبق التغييرات غير المنفذة بالترتيب.

من ينشئ database نفسها؟ في إعدادنا، تقوم MySQL image بإنشائها عند أول تهيئة لـvolume، اعتماداً على MYSQL_DATABASE. ثم تأتي migrations لإعداد tables والتعديلات التي يحتاجها التطبيق.

ما دور data-source.ts؟ إعطاء TypeORM بيانات الاتصال ومواقع entities وmigrations. كان يبحث داخل src عن ملفات .ts، بينما production image تحتوي الملفات المبنية داخل dist بامتداد .js؛ لذلك عدلنا طريقة إيجادها.

ما دور الأمر الجديد؟ يشغّل TypeORM CLI باستخدام JavaScript المبني، دون الاعتماد على ts-node لتشغيل ملفات TypeScript.

مثال: إذا احتاج إصدار جديد إلى column إضافي، يجب نجاح migration قبل تشغيل backend الذي سيستعمل ذلك column. وإذا فشلت، يمنع ترتيب التشغيل بدء backend الجديد.

حدود مسؤوليتك: إعداد طريقة التشغيل ومتابعة النتيجة من مسؤولية DevOps. أما كتابة التغييرات في schema فتُنسَّق مع مسؤول backend. ويمكن لـNode.js تنفيذ SQL queries مباشرة؛ استخدام TypeORM اختيار لتنظيم العمل وليس شرطاً تفرضه اللغة.

عُدِّل ملف إعداد الاتصال وmigrations التالي:

apps/backend/src/database/data-source.ts

أصبحت المسارات تُحدَّد انطلاقاً من موقع ملف الإعداد، وبالامتداد الموافق للنسخة المستخدمة: ملفات TypeScript في development، وملفات JavaScript المبنية في production.

أُضيف أمر تشغيل migrations في production إلى إعدادات package.json:

npm run migration:run:prod

لم يتغير محتوى migrations نفسها، وبقيت أوامر development وإعداد منع تعديل الجداول تلقائياً كما كانت.

نتيجة التحقق: عثر النظام داخل production image على 24 entity و3 migrations مبنية، دون تحميل أداة تشغيل ملفات development. كما اكتمل تنفيذ migrations بنجاح في local environment.

3.4. إنشاء إعداد مستقل لـproduction containers

ما دور Compose؟ وصف services التي تعمل معاً: ما image كل واحدة، وما command وenvironment variables وvolumes وnetworks الخاصة بها، وبأي ترتيب تبدأ.

لماذا نحتاجه بعد Dockerfile؟ يبني Dockerfile صورة التطبيق فقط. أما Compose فيشغل التطبيق مع MySQL وNginx ويصلها ببعضها.

لماذا يستخدم migrate وbackend الصورة نفسها؟ تحتوي image كود التطبيق وملفات migrations معاً. يشغّل backend الأمر الافتراضي للسيرفر، بينما يستبدل migrate ذلك بأمر الترحيلات عبر إعداد command، ثم يخرج. الصورة واحدة، لكنهما containers مستقلان.

ما دور depends_on؟ انتظار الشروط المحددة: نجاح MySQL health check، ثم انتهاء migrate بـexit code 0، ثم جاهزية backend قبل تشغيل Nginx.

ما دور networks؟ تمكين containers من الوصول إلى بعضها بأسماء services. لهذا يستعمل backend العنوان mysql للاتصال بـdatabase، ويستعمل Nginx العنوان backend:3000.

لماذا عزل database network؟ لجعل الوصول إلى MySQL داخلياً، دون نشر port 3306 على الجهاز. كما يمنح اسم Compose project بيئة الإنتاج موارد مستقلة عن development.

أُنشئ الملف التالي، مع إبقاء إعداد development مستقلاً:

docker-compose.prod.yml

اسم Compose project:

transcendence-prod
service مسؤوليتها
mysql تشغيل database، مع persistent volume وhealth check بSQL query فعلي
migrate تنفيذ migrations ثم الخروج بنجاح
backend تشغيل التطبيق باستخدام production image نفسها
nginx استقبال الطلبات، وتوفير TLS، وتوجيهها إلى التطبيق

ترتيب البدء هو: جاهزية database، ثم نجاح migrations، ثم جاهزية التطبيق، ثم بدء Nginx reverse proxy.

لا تنشر database ولا التطبيق ports مباشرة على الجهاز. وينشر Nginx reverse proxy الـports 80 و443 على عنوان الجهاز المحلي فقط. كما عُزلت network database عن external network.

3.5. اختبار persistent storage

ما دور volume؟ حفظ البيانات خارج العمر المؤقت لـcontainer. لذلك يمكن حذف container وإعادة إنشائه مع ربط volume نفسه، فتعود البيانات الموجودة.

لماذا نحتاج اثنين؟ يخزن MySQL volume بيانات database، بينما يخزن backend storage volume محتوى uploaded files. وجود معلومات ملف داخل database لا يعني أن الملف نفسه محفوظ فيها.

مثال: يحتوي database اسم وثيقة ومسارها وصاحبها، بينما يوجد محتواها داخل storage volume. يجب الحفاظ على الاثنين كي يبقى تنزيل الوثيقة ممكناً بعد deployment.

ما الذي أثبته الاختبار؟ أن استبدال containers لا يحذف البيانات المرتبطة بـvolumes. لكنه لا يحمي من حذف volume أو تلف القرص؛ وهنا نحتاج backup.

أُعدت وحدتا volume مستقلتان عن development environment:

volume محتواها
transcendence-prod_mysql_data بيانات database
transcendence-prod_backend_storage uploaded files داخل مجلد storage

أُضيف record مؤقت وملف تجريبي، ثم أُعيد إنشاء containers الخاصة بـMySQL وmigrate وbackend. تغيرت معرفات containers، بينما بقيت volumes نفسها، وبقي record والملف محفوظين. وأُزيلت بيانات الاختبار بعد التحقق.

يثبت ذلك استمرار البيانات عند استبدال containers. أما الحماية من حذف volumes أو فقدان الجهاز فتتطلب backups مستقلة.

3.6. إعداد Nginx reverse proxy وlocal TLS

ما دور Nginx؟ أن يكون نقطة دخول واحدة: يستقبل requests، ويدير HTTPS، ثم يمرر الطلب إلى backend. يستعمل إعدادنا Nginx image جاهزة، لذلك لم نحتج إلى Dockerfile خاص بها.

ما دور nginx.conf؟ تحديد ports وقواعد routing وملفات TLS وطريقة تمرير WebSocket. تُربط هذه الإعدادات داخل container للقراءة فقط باستعمال ro.

العنصر دوره
port 80 استقبال HTTP وإرجاع redirect إلى HTTPS
port 443 استقبال HTTPS وإنهاء اتصال TLS عند Nginx
proxy_pass إرسال الطلب إلى backend:3000 عبر Docker network
fullchain.pem تقديم TLS certificate إلى العميل للتحقق من هوية العنوان
privkey.pem المفتاح السري الذي يستخدمه Nginx في TLS handshake؛ لا يُشارك ولا يُحفظ في Git
Upgrade وConnection السماح بانتقال الاتصال من HTTP إلى WebSocket
client_max_body_size تحديد الحجم الأقصى للطلب قبل إرساله إلى backend

لماذا الشهادة المحلية؟ نحتاج HTTPS أثناء العمل على localhost. شهادة self-signed توفر التشفير، لكن المتصفح لا يثق بها تلقائياً. لذلك استخدم الاختبار CA trust صريحاً للشهادة المحلية.

مهم: كتابة 443:80 في Compose لا تنشئ TLS. يلزم 443:443 مع إعداد listen 443 ssl والشهادة والمفتاح. بعد إنهاء TLS يستطيع Nginx التواصل داخلياً مع backend باستخدام HTTP وفق متطلبات الموضوع.

أُنشئ ملف إعداد Nginx reverse proxy:

nginx/nginx.conf

يشمل الإعداد:

  • تحويل طلبات HTTP إلى اتصال HTTPS، باستخدام HTTP status code 308.
  • دعم TLS 1.2 وTLS 1.3.
  • توجيه الطلبات إلى التطبيق على الـinternal port 3000.
  • دعم WebSocket upgrade إلى اتصال WebSocket.
  • تمرير معلومات الطلب وإضافة بعض security headers.
  • السماح بطلب حجمه 11 MiB لاستيعاب ملف حجمه 10 MiB مع بيانات النموذج الإضافية.

وُلِّدت شهادة self-signed TLS محلية، صالحة لاسم الجهاز المحلي وعنوانه، داخل المجلد التالي:

nginx/certs/

حُمي private key باستخدام permissions 600، واستُثني المجلد من التتبع في Git. TLS certificate صالحة لمدة سنة، وتجديدها حالياً يدوي.

نتيجة التحقق: نجح فحص إعداد Nginx reverse proxy، وعمل health check عبر اتصال HTTPS، ونجح تحويل اتصال HTTP. ويظهر تحذير المتصفح إذا لم تكن شهادة TLS المحلية موثوقة لديه.

3.7. اختبار اتصال Socket.IO عبر TLS

ما دور Socket.IO؟ إبقاء اتصال يسمح بإرسال events بين العميل وbackend دون انتظار طلب منفصل لكل تحديث، كما في المحادثة والتنبيهات.

لماذا اختباره خلف Nginx؟ قد تعمل API requests العادية بينما تفشل ترقية WebSocket بسبب إعدادات proxy. لذلك لا يكفي نجاح /health لإثبات صحة الاتصال اللحظي.

ما الذي اختبرناه؟ بدأ client باستخدام HTTPS polling، ثم انتقل إلى WSS. واستخدم JWT يثبت هوية الحساب، بينما أكد وصول workspace-chat.ready قبول الاتصال من التطبيق.

الفرق بين JWT وTLS: يحدد JWT هوية المستخدم، بينما يحمي TLS الاتصال أثناء النقل. نحتاج الاثنين لأنهما يؤديان وظيفتين مختلفتين.

أُنشئ حساب مؤقت، ونُفِّذ login عبر اتصال HTTPS مع التحقق من شهادة TLS المحلية. ثم استُخدم JWT للاتصال، ووصل event تأكيد جاهزية المحادثة:

workspace-chat.ready

تأكدنا من WebSocket upgrade من polling إلى اتصال WSS عبر Nginx reverse proxy. وبعد الاختبار نُفِّذ logout وحُذف الحساب المؤقت.

شمل الاختبار الاتصال وauthentication وWebSocket upgrade؛ ولم يشمل تبادل الرسائل بين عدة مستخدمين.

3.8. اختبار recovery بعد التوقف

ما دور restart: unless-stopped؟ إعادة تشغيل container إذا انتهت عملية التشغيل، ما لم يكن قد أُوقف عمداً. وهو لا يعيد تنفيذ migrations تلقائياً عند كل restart للـbackend.

لماذا اختبرنا MySQL restart أيضاً؟ لأن عودة container إلى العمل لا تكفي؛ يجب أن يستعيد التطبيق الاتصال بـdatabase ويستقبل requests بصورة صحيحة.

لماذا استخدمنا login request؟ مسار /health الحالي يعيد استجابة ثابتة. أما محاولة login فتصل إلى database للبحث عن الحساب، لذلك ساعدت على التحقق من عودة الاتصال الفعلي.

حدود الإعداد: وصف container بأنه unhealthy لا يجبر Docker وحده على تنفيذ restart. تعتمد سياسة restart هنا على انتهاء عملية container، لا على نتيجة health check فقط.

  • أُوقفت backend process فجأة لمحاكاة crash. فأعاد نظام containers تشغيله تلقائياً.
  • أُعيد تشغيل database، وانتُظر نجاح health check الخاص بها.
  • تم التحقق من عودة اتصال HTTPS، ومن قدرة التطبيق على تنفيذ طلب login يعتمد على database.

استُخدمت بيانات دخول غير صحيحة، وكانت HTTP status code المتوقع 401. وقد أثبت ذلك وصول التطبيق إلى database، بدلاً من الاعتماد على مسار health check وحده.

لم يُعدَّل backend code ولم تُحذف بياناته الموجودة خلال هذه الاختبارات.

3.9. استكمال مثال environment variables ودليل التشغيل

ما دور .env؟ تمرير إعدادات وsecrets دون تثبيتها داخل source code أو image، مثل بيانات اتصال database وJWT_SECRET.

ما دور .env.example؟ تعريف أسماء الإعدادات المطلوبة وتقديم قيم غير سرية تساعد عضواً آخر على إعداد بيئته. لا يحتوي نسخة من secrets الحقيقية.

ما دور .gitignore؟ منع إضافة الملفات المحلية إلى Git بصورة اعتيادية. لذلك استثنينا .env وprivate keys وbackups. وهو لا يشفر الملفات ولا يحميها وحده من الوصول على الجهاز.

لماذا كتبنا دليل التشغيل؟ حتى يستطيع شخص آخر تشغيل البيئة وفحصها والتعامل مع logs دون الاعتماد على ذاكرة شخص واحد. وما زال README الكامل يحتاج معلومات الفريق والخصائص والـmodules.

أُعيد إنشاء مثال environment variables بالقيم الافتراضية العادية، مع ترك secrets فارغة:

.env.example

شمل المثال JWT_SECRET المطلوب وإعدادات التكامل الاختيارية. ولم يتغير ملف secrets الفعلي.

كُتب دليل التشغيل المحلي، وأُضيف رابطه إلى ملف README الرئيسي:

docs/deployment/LOCAL_PRODUCTION.md

يوثق الدليل المتطلبات، وإعداد البيئة وTLS certificate، والتشغيل، وlogs، والفحوصات، وstorage، والإيقاف دون حذف البيانات. ولا يزال ملف README الكامل المطلوب في الموضوع الرسمي غير مكتمل.

3.10. إعداد backup وrestore واختبارهما

ما دور backup؟ الاحتفاظ بنسخة مستقلة يمكن الرجوع إليها إذا حُذفت البيانات أو تلفت. أما restore فهو إعادة تكوين database والملفات انطلاقاً من تلك النسخة.

لماذا يوقف backup.sh التطبيق مؤقتاً؟ حتى لا تتغير بيانات ملف أو معلوماته داخل database بين لحظة نسخ الأولى والثانية. الهدف أخذ لقطة متناسقة، مع افتراض عدم وجود عمليات أخرى تكتب مباشرة في database أثناء النسخ.

ناتج backup ما الذي يحتويه أو يثبته؟
database.sql.gz أوامر SQL لإعادة إنشاء tables واسترجاع البيانات، ينتجها mysqldump ثم يضغطها gzip
files.tar.gz أرشيف لمحتوى storage، بما فيه uploaded files
backend-image.txt معرف backend image المستخدمة وقت النسخ، للمساعدة على مطابقة إصدار التطبيق
mysql-image.txt معرف MySQL image المستخدمة وقت النسخ
SHA256SUMS بصمات checksums للتحقق من عدم تغير الملفات مقارنة بالنسخة المسجلة

تنبيه لفهم الملفات: لا تخزن ملفات معرفات images الصور نفسها. كما أن الضغط وchecksums لا يعنيان أن محتوى backup مشفر؛ لذلك تبقى النسخة بيانات خاصة تحتاج الحماية.

ما دور restore-test.sh؟ إنشاء Compose project جديد وvolumes جديدة، واستيراد SQL واستخراج الملفات، ثم تشغيل الخدمات وفحص الوصول إلى database وحالة migrations. ويرفض الكتابة فوق موارد موجودة لحماية البيئة الأصلية.

لماذا حذفنا بيانات الاختبار من المصدر قبل restore؟ لإثبات أن السجل والملف رجعا فعلاً من backup، وليس لأن الاختبار ما زال يقرأ النسخة الأصلية.

ما الذي لا يزال ناقصاً؟ scheduled backups وretention policy وoff-machine copy وإجراء واضح لاستبدال بيئة متضررة بأخرى مسترجعة. النسخ محفوظة حالياً على الجهاز نفسه، وrestore-test يتحقق من الاسترجاع المعزول فقط.

أُنشئت الأدوات التالية:

الملف وظيفته

تسلسل الاختبار:

  2. أخذ backup منهما مع بقية البيانات.

  4. تنفيذ restore للنسخة في volumes جديدة ومعزولة.
  5. التأكد من عودة record والملف بالمحتوى نفسه.
  6. التحقق من الاتصال بالـdatabase وحالة migrations.
  7. إزالة موارد الاختبار وأخذ نسخة نظيفة من البيئة الأصلية.

5. المهام المتبقية حسب الأولوية

  1. ترتيب نسخة محمية من backup خارج الجهاز؛ اكتملت الجدولة اليومية وretention policy واختبار restore المعزول.
  2. متابعة نواقص application logging مع فريق Backend؛ اكتمل Docker log rotation وإعداد Nginx access logs. ويلزم centralized logging باستخدام حزمة ELK إذا اختار الفريق احتساب الوحدة الكبرى الخاصة بها.
  3. تحديد نطاق monitoring. وعند اختيار وحدة Prometheus/Grafana الكبرى، يلزم جمع metrics وdashboards مخصصة وalerts وتأمين الولوج. وتعديلات application metrics من مسؤولية صاحب backend.
  4. استكمال status page وإجراءات disaster recovery للوحدة الصغرى المختارة. اكتملت automated backups، ولكن مسار health check ونجاح backup وحدهما لا يكملان الوحدة.
  5. تنسيق إعدادات CORS وربط frontend ومتطلبات التكامل الخارجي، ثم اختبار multi-user support والمتصفح عند جاهزية الخصائص.
  6. اعتماد image tags واضحة للإصدارات، وتوثيق deployment، وتجربة rollback مع مراعاة توافق database، واستكمال دليل disaster recovery.
  7. تحويل الفحوصات اليدوية إلى إجراء قابل للتكرار، واستكمال failure tests المناسبة.
  8. استكمال ملف README للمشروع بالإنجليزية، بما يشمل الأدوار والمساهمات وarchitecture والخصائص والوحدات وحساب النقاط والتشغيل واستخدام الذكاء الاصطناعي.
  9. إضافة فحوصات CI ونشر images وإضافة deployment automation المتفق عليها في نهاية الخطة.

حجم العمل المتبقي: لا توجد نسبة إنجاز أو مدة موثوقة حالياً؛ إذ يتوقف الجهد على الوحدات الاختيارية التي سيعتمدها الفريق وعلى جاهزية frontend. أساس التشغيل المحلي يعمل، وتتركز المهام المتبقية في monitoring وautomation وrelease management والتعافي.

تُحسب نقاط التقييم الرسمي بصورة مستقلة وفق الوحدات المكتملة؛ فعدد المراحل في هذا التقرير لا يساوي عدد النقاط.

10. تحديث بتاريخ 7 نوفمبر 2026: إعداد Docker log rotation

الدور والسبب

تسجل services أحداث التشغيل وأخطاءها في stdout وstderr، ويجمعها Docker. تساعد هذه logs على تحديد مصدر المشكلة: هل فشل Nginx في الاتصال بـbackend، أم ظهرت مشكلة داخل التطبيق أو MySQL أو migrations؟

قبل التعديل كانت الخدمات الأربع تستعمل json-file دون حدود حجم صريحة. أُضيف الإعداد نفسه لكل service في docker-compose.prod.yml:

logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

كيف يعمل؟

  • يحفظ json-file logging driver مخرجات container في ملفات يديرها Docker على الجهاز.
  • عند وصول ملف log إلى حدود 10 MB، ينشئ Docker ملفاً جديداً تلقائياً.
  • يحتفظ بما يصل إلى 3 ملفات لكل container، شاملة الملف الحالي، ويحذف الأقدم عند الحاجة.
  • السعة التقريبية 30 MB لكل container، وليست للمشروع كله. ولا يتعلق هذا الإعداد بـdatabase volumes أو backup retention.
  • لا يحتاج rotation إلى cron أو scripts إضافية، ولا يجمع ملفات داخلية أخرى لا تُكتب إلى stdout أو stderr.

قراءة logs

docker compose -f docker-compose.prod.yml logs --follow --timestamps --tail=100 backend

يمكن استبدال backend باسم nginx أو mysql أو migrate. ويوقف Ctrl+C عرض logs فقط، ولا يوقف container.

التطبيق والحدود

يتطلب تغيير إعداد logging إعادة إنشاء containers؛ لا يكفي restart. يُطبق الإعداد مع الاحتفاظ بنفس images وvolumes، واستعمال backup lock لمنع التداخل مع النسخ. لا يحتفظ هذا الإعداد بـlogs الخاصة بالـcontainers المحذوفة؛ يلزم تصديرها مسبقاً عند الحاجة إليها.

هذه الخطوة تضبط local log rotation فقط، ولا تكمل ELK Major. تبقى centralized logging وarchiving وتنسيق application logs حسب الوحدات المختارة والتنسيق مع مسؤول backend. ولا يتغير backend code.

نتيجة التحقق: أُعيد إنشاء الخدمات الأربع بنجاح، وتأكدنا من تطبيق json-file وmax-size: 10m وmax-file: 3 فعلياً على كل container ومن إمكانية قراءة logs. بقيت image IDs وvolume names كما كانت، وعاد MySQL وbackend إلى healthy، وانتهى migrate بالرمز صفر، ونجح HTTPS health request مع التحقق من الشهادة. لم نولد logs ضخمة لاختبار الوصول إلى حد الحجم؛ التحقق شمل إعدادات Docker الفعلية وعمل الخدمات.

اتُّفق على مراجعة الـ PDFs قبل كل مرحلة، وشرح نطاق التغيير قبل تنفيذه، وذكر جميع الملفات والإجراءات التي تغيرت بعد التنفيذ. لا يُعدَّل Backend code؛ يتولى فريق Backend محتوى application logs وسلوك التطبيق، ويتولى مسؤول DevOps إعدادات البنية التشغيلية. يمكن متابعة مراحل DevOps مع توثيق النواقص وإحالتها إلى الفريق، دون اعتبار application logging مكتملة.

ما أثبتته القراءة وما أثبتته التجربة

رفض login وSocket.IO في هذين الاختبارين عمل بصورة صحيحة؛ الملاحظة هي غياب تسجيل الرفض في Backend logs. وقد تظهر معلومات الطلب الأساسية في Nginx access logs، وهي ليست بديلاً عن سبب الحدث داخل التطبيق.

فهم مشكلة حذف files من الصفر

لكل uploaded file محتوى فعلي في storage وrecord في Database يصف اسمه ومالكه ومساره. في FilesService.remove() يُحفظ deletedAt أولاً، ثم تُجرّب إزالة المحتوى الفعلي. يسمى تعليم الـrecord بهذه الطريقة soft delete.

يستعمل التنفيذ الحالي:

await unlink(absolutePath).catch(() => undefined);

يحاول unlink حذف الـfile. وإذا فشل، تتجاهل catch الخطأ وتسمح باستمرار التنفيذ. لذلك يمكن أن يصبح الـrecord معلماً كمحذوف بينما يبقى المحتوى في storage، ثم تُنشأ FILE_DELETED activity وتعود العملية بنجاح. عند تكرار هذا الفشل يمكن أن تتراكم ملفات لا تظهر للمستخدم وتستهلك المساحة. لا يعني ذلك أن جميع عمليات الحذف تفشل.

التجربة الفعلية المعزولة: شُغلت النسخة المبنية من FilesService الموجودة في production image داخل Node.js process منفصلة. استُعمل repository في الذاكرة ومحاكاة للخدمات التابعة، مع file حقيقي مؤقت داخل /tmp. مُنعت صلاحية الحذف من المجلد، وتأكدنا أن النظام يرجع EACCES عند محاولة حذفه بالمستخدم node ذي UID 1000.

أعادت remove() النجاح، وحفظت deletedAt في repository التجريبية، وطلبت إنشاء FILE_DELETED activity، بينما بقي الـfile موجوداً ولم تُستدعَ وظائف service logger. هذا اختبار لسلوك الخدمة المبنية مع فشل حقيقي في filesystem، وليس اختبار HTTP كاملاً ولا دليلاً على وجود ملفات عالقة حالياً في بيانات المشروع.

أُعيدت صلاحية المجلد المؤقت وحُذف بعد الاختبار. لم تُستخدم بيانات MySQL أو storage volume الخاصة بالمشروع، ولم يُعدَّل Backend code أو يُعد تشغيله. نجح طلب /health عبر HTTPS بعد التجارب بالرمز 200.

المتابعة مع فريق Backend

أُعدت رسالة بالإنجليزية ليُرسلها مصطفى إلى الفريق، توضح نتيجة تجربة الحذف ونقص تسجيل رفض Authentication وSocket.IO، وتطلب مراجعة معالجة فشل الحذف وتسجيله وretry المناسب. لم تُرسل الرسالة إلى الفريق عبر أي أداة. يبقى القرار والتنفيذ داخل التطبيق من مسؤولية الفريق، ويمكن مواصلة بقية أعمال DevOps بالتوازي.

12. تحديث بتاريخ 7 نوفمبر 2026: تقليل البيانات الحساسة في Nginx access logs

ما المشكلة؟

يمر طلب GitHub OAuth callback عبر Nginx وقد يحتوي على query parameters مثل code وstate. الـcode قيمة مؤقتة تُستخدم للحصول على access token، والـstate يساعد في ربط الرد بعملية OAuth التي بدأها التطبيق.

كان access log format الافتراضي يسجل سطر الطلب كاملاً، وقد يشمل هذه القيم. كما أن Referer قد يحتوي على URL مع قيم حساسة. أكدت المراجعة وجود هذا الاحتمال في الإعداد، ولم تثبت تسجيل OAuth code حقيقي. يحمي HTTPS الاتصال أثناء النقل، لكنه لا يمنع Nginx من تسجيل الطلب بعد فك تشفيره.

ما الذي تغير وما دور كل جزء؟

أُضيف إلى قسم http في nginx/nginx.conf:

log_format app_access '$remote_addr [$time_iso8601] '
                      '"$request_method $uri $server_protocol" '
                      '$status $body_bytes_sent '
                      'request_time=$request_time '
                      'upstream_time=$upstream_response_time';
access_log /dev/stdout app_access;
الإعداد دوره
log_format app_access تعريف صيغة محددة لسطر access log
$remote_addr عنوان الطرف المتصل كما يراه Nginx
$time_iso8601 وقت الطلب مع معلومات المنطقة الزمنية
$request_method نوع الطلب مثل GET أو POST
$uri الـpath بعد normalization دون query parameters
$server_protocol نسخة HTTP
$status رمز النتيجة مثل 200 أو 401
$body_bytes_sent حجم المحتوى المرسل دون response headers
$request_time مدة معالجة الطلب كاملة لدى Nginx بالثواني
$upstream_response_time مدة الاستجابة من Backend؛ تظهر - عند عدم الاتصال به، مثل redirect
access_log /dev/stdout app_access استعمال الصيغة في HTTP وHTTPS وإرسال الأسطر إلى Docker لتطبيق log rotation الحالي

لا تتضمن الصيغة query parameters أو Referer أو User-Agent أو Authorization أو cookies أو request body. ويظل الـpath مسجلاً، لذلك يجب ألا يحتوي هو نفسه على secrets.

مثال بقيم وهمية يوضح الفرق:

Before: GET /github/callback?code=EXAMPLE_CODE&state=EXAMPLE_STATE HTTP/1.1
After:  GET /github/callback HTTP/1.1

تصل query parameters كاملة إلى Backend، ويحتفظ بها HTTP to HTTPS redirect أيضاً. التغيير في التسجيل فقط، ولم يُعدَّل Backend code أو proxy_pass أو Compose.

كيف طُبق الإعداد وكيف اختُبر؟

نجح nginx -t أولاً، ثم طُبق nginx -s reload. بقي container ID ووقت بدء الـcontainer كما هما؛ لم يحدث container restart أو إعادة إنشاء. يسمح graceful reload بتطبيق الإعداد مع إنهاء أعمال الـworkers القديمة تدريجياً.

أُرسلت طلبات بقيم اختبارية فريدة في code وstate وReferer وUser-Agent وCookie وAuthorization، ثم فُحصت logs الجديدة:

  • نجح /health عبر HTTPS بالرمز 200 مع التحقق من شهادة TLS.
  • أعاد HTTP الرمز 308 مع الاحتفاظ بالـquery الأصلية في Location.
  • نجح Engine.IO polling handshake بالرمز 200 عبر Nginx. ويثبت ذلك وصول قيمتي EIO وtransport المطلوبتين إلى Backend؛ لا يمثل هذا اختبار WebSocket upgrade أو OAuth كاملاً.
  • أُغلقت Engine.IO session التجريبية بعد التحقق.
  • ظهرت أسطر الطلبات مع الـpath وstatus وtimings، دون القيم الوهمية أو query parameters.
  • بقي Backend وMySQL بحالة healthy، وmigrate منتهياً بالرمز 0.

حدود الإصلاح: يشمل access logs الجديدة. لا يعيد كتابة logs السابقة ولا يمسحها، ولا يغير Nginx error logs أو Backend logs. وقد تتضمن error logs تفاصيل الطلب عند بعض الأعطال؛ لم نفتعل هذه الأعطال في اختبار الإصلاح، ولذلك لا يمثل هذا ضماناً عاماً لإخفاء جميع secrets من جميع logs.

اعتمد الإعداد على توثيق Nginx الخاص بـ logging، وطريقة تطبيقه على توثيق Nginx الخاص بـ reload.

الملفات والإجراءات الخاصة بهذا التحديث

  • عُدّل nginx/nginx.conf لإعداد access logs.
  • عُدّل docs/deployment/LOCAL_PRODUCTION.md لتوثيق الإعداد وطريقة reload وحدوده.
  • عُدّل هذا التقرير docs/deployment/PROGRESS_2026-11-05.md، وأُعيد توليد نسخته HTML مع الحفاظ على اتجاه العربية وكتابة مصطلحات IT بالإنجليزية.
  • صُحح جدول التقدم وقائمة المهام المتبقية ليعكسا اكتمال automatic backup وretention وlog rotation، وأُضيفت نتائج مراجعة Backend وتجاربها وتقسيم المسؤوليات.
  • لم تُضف أو تُحذف ملفات من المشروع في هذا التحديث. الإجراء التشغيلي هو Nginx reload وطلبات الاختبار؛ لم يتغير cron أو Backend code أو بيانات Database أو storage.

14. تحديث بتاريخ 7 نوفمبر 2026: أساس Prometheus وGrafana

دور المكونات

يجمع Prometheus قياسات رقمية بصورة دورية ويحتفظ بتاريخها. يستعلم Grafana عن هذه القياسات لعرضها. لا يجمع Grafana قياسات الجهاز والتطبيق تلقائياً بمجرد تشغيله.

Browser -> HTTPS Nginx /grafana/ -> Grafana -> Prometheus
                                              |
                                              v
                                    Prometheus self-metrics

الـ target الوحيد في هذه الخطوة هو Prometheus نفسه. تعني نتيجة 1 للاستعلام التالي نجاح جمع قياساته، ولا تعني أن Backend أو MySQL سليم:

up{job="prometheus"}

الوصول والحماية

عنوان الواجهة هو https://localhost/grafana/. اسم المستخدم الأولي admin، وكلمة السر موجودة في .env تحت GRAFANA_ADMIN_PASSWORD. وُلّد GRAFANA_SECRET_KEY مستقلاً لحماية الأسرار التي يخزنها Grafana، ويجب الاحتفاظ به. لا تُعرض القيم السرية في التقرير.

عُطّل anonymous access وself-registration، وفُرض HTTPS على session cookies. متغيرات الحساب الأولي تُستعمل عند تهيئة volume جديدة؛ تعديل كلمة السر في .env لاحقاً لا يعيد تعيين كلمة سر حساب موجود، ويجب استعمال إدارة الحسابات داخل Grafana.

لا توجد host ports جديدة للخدمتين. يستعمل Grafana شبكة monitoring الداخلية للاتصال بـPrometheus وشبكة application للوصول من Nginx. يُحل اسم Grafana عبر Docker DNS وقت الطلب حتى لا يمنع توقفه بدء Nginx أو تشغيل مسارات Backend.

التخزين والموارد

  • يحفظ prometheus_data تاريخ القياسات داخل /prometheus.
  • يحفظ grafana_data المستخدمين والإعدادات وdashboards المستقبلية داخل /var/lib/grafana.
  • يحتفظ Prometheus بالقياسات حتى 7 أيام، مع حد 512 MB للـ stored blocks. تحتاج WAL وhead data مساحة إضافية؛ ليس ذلك سقفاً صارماً لحجم الـ volume كله.
  • حد RAM الأولي 256 MiB لـPrometheus و512 MiB لـGrafana، مع حد CPU واحد لكل خدمة. تُراجع هذه الحدود عند توسيع المراقبة.
  • تطبق الخدمتان log rotation بحجم 10 MB و3 ملفات، مع إسقاط Linux capabilities ومنع اكتساب صلاحيات إضافية.
  • لا يشمل backup script الحالي بيانات المراقبة؛ فهو ينسخ بيانات التطبيق وuploaded files. تبقى طريقة استرجاع بيانات المراقبة عملاً منفصلاً.

لم تُضف بعد exporters الخاصة بالجهاز والـ containers وMySQL وHTTPS. وتبقى قياسات API error rate وcustom dashboards وalert rules ووجهة الإشعارات. تشغيل الخدمتين وحده لا يكمل Monitoring Major، وأي instrumentation يتطلب تعديل التطبيق يبقى من مسؤولية فريق Backend.

نتائج الاختبارات والإجراءات التشغيلية

  • نجح فحص Compose وpromtool check config.
  • فشلت البداية باستعمال Grafana 13.3.0 عند data-source provisioning برسالة data source not found. استُعمل الإصدار الرسمي المحدّث 12.4.14، وأُعيدت تهيئة Grafana volume الجديدة لهذه المحاولة فقط؛ لم تمس أي بيانات سابقة للتطبيق. قد تبقى image المحاولة الأولى في Docker cache.
  • أصبحت الخدمتان healthy، ونجح فحص Nginx ثم reload.
  • نجح تحميل صفحة login وملف JavaScript عبر HTTPS تحت /grafana/، مع التحقق من الشهادة.
  • رُفض الوصول إلى data-source API دون حساب بالرمز 401. نجح admin login الفعلي وأُنشئت secure session cookie.
  • نجح data-source health check، وأعاد الاستعلام عبر Grafana قيمة 1 لـup{job="prometheus"}.
  • أُعيد إنشاء containers المراقبة فقط للتحقق من persistence. تغيرت معرفاتها مع الاحتفاظ بالـ volumes نفسها، ونجح الدخول مجدداً واسترجاع قياس بتاريخ سابق لإعادة الإنشاء.

  • أُغلقت جلسة الدخول التجريبية. لم تُنشأ cron job جديدة أو exporters أو custom dashboards أو alert rules أو إشعارات خارجية.

23. إضافة Alerts إلى Monitoring

كيف تعمل Alerts؟

  • pending: ظهر الشرط، لكن مدة الانتظار لم تكتمل.
  • firing: استمر الشرط طوال مدة الانتظار.
  • resolved: عاد الوضع الطبيعي، فيختفي Alert من جدول الحالات النشيطة.

مثلاً: استمرار انقطاع Backend لمدة دقيقة يؤدي إلى firing. ارتفاع CPU فوق 90% يحتاج عشر دقائق، وانخفاض RAM أو Disk المتاحة تحت 10% يحتاج خمس دقائق. ارتفاع API 5xx فوق 5% يحتاج دقيقتين، مع وجود 20 request على الأقل خلال خمس دقائق. توجد جميع الشروط في Operating guide.
