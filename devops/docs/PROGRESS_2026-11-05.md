### 3.2. Preparing the production image

**What does a Dockerfile do?** It describes how to build a Docker image: the Node.js version, dependencies, build steps, and default startup command. The image is the built result; a container is a running instance of it.

**Why keep it separate from `Dockerfile.dev`?** Development uses watch mode to restart when code changes. Production runs the built application without relying on development tools or source files mounted from the host.

| Component | Role in this setup |
| --- | --- |
| Build stage | Install dependencies and run `npm run build` to generate JavaScript in `dist` |
| `npm ci` | Reproducibly install the versions specified in `package-lock.json` |
| `npm prune --omit=dev` | Remove development dependencies after the build |
| Runtime stage | Keep the built application and the dependencies needed to run it |
| `USER node` | Run the application without root privileges |
| `EXPOSE 3000` | Document the application port; this does not publish it on the host |
| `CMD` | Set the default startup command to run `dist/main.js` |

**Example:** The same image can run on another machine with its packaged Node.js runtime and dependencies. Environment variables and volumes are supplied separately at runtime.

The production build file was created at:

```text
apps/backend/Dockerfile
```

The build has two stages:

1. Install dependencies, compile the source, and remove development dependencies.
2. Copy the built application and production dependencies into the runtime image.

The backend runs as the `node` user, without watch mode or a host source-code mount. A writable directory was also prepared for uploaded files.

**Validation:** The production image built successfully. The dependency audit reported 36 vulnerabilities in the full installation and 6 after removing development dependencies. These findings have not yet been individually reviewed or remediated.

### 3.3. Preparing database migrations for production

**What do migrations do?** They apply ordered changes to the database schema, such as creating a table or adding a column. TypeORM tracks executed migrations in `typeorm_migrations` and applies pending migrations in order.

**What creates the database itself?** In this setup, the MySQL image creates it during initial volume initialization using `MYSQL_DATABASE`. Migrations then create the tables and apply the changes required by the application.

**What does `data-source.ts` do?** It provides TypeORM with connection settings and the locations of entities and migrations. It previously looked for `.ts` files under `src`, while the production image contains built `.js` files under `dist`. The path resolution was adjusted to support both.

**What does the new command do?** It runs the TypeORM CLI against built JavaScript without relying on `ts-node` to execute TypeScript source files.

**Example:** If a new release requires an additional column, the migration must succeed before starting the backend that uses it. If the migration fails, the configured startup order prevents the new backend from starting.

**Responsibility boundary:** DevOps owns execution and result checking. Schema changes must be coordinated with the backend owner. Node.js can execute SQL queries directly; TypeORM is an organizational choice, not a language requirement.

The following connection and migration configuration file was updated:

```text
apps/backend/src/database/data-source.ts
```

Paths now resolve relative to the configuration file, using the extension appropriate to the running version: TypeScript in development and built JavaScript in production.

A production migration command was added to `package.json`:

```bash
npm run migration:run:prod
```

The migration contents were not changed. Existing development commands and the setting that prevents automatic schema synchronization were retained.

**Validation:** The production image discovered 24 entities and 3 built migrations without loading `ts-node`. Migration execution also completed successfully in the local environment.

### 3.4. Creating a separate production Compose setup

**What does Compose do?** It describes services that run together: their images, commands, environment variables, volumes, networks, and startup dependencies.

**Why is it needed in addition to a Dockerfile?** The Dockerfile builds the application image. Compose runs it alongside MySQL and Nginx and connects them.

**Why do `migrate` and `backend` use the same image?** The image contains both application code and migration files. The backend uses the default server command; the migration service overrides it with the migration command and then exits. They are separate containers using the same image.

**What does `depends_on` do here?** It waits for the configured conditions: a successful MySQL health check, migration completion with exit code 0, and backend readiness before starting Nginx.

**What do networks do?** They allow containers to reach each other by service name. The backend connects to the database at `mysql`, and Nginx connects to `backend:3000`.

**Why isolate the database network?** MySQL remains internal, without publishing port 3306 on the host. The Compose project name also separates production resources from development resources.

The following file was created while keeping development configuration separate:

```text
docker-compose.prod.yml
```

Compose project name:

```text
transcendence-prod
```

| Service | Responsibility |
| --- | --- |
| `mysql` | Run the database with a persistent volume and a health check that executes a real SQL query |
| `migrate` | Execute migrations and exit successfully |
| `backend` | Run the application using the same production image |
| `nginx` | Receive requests, terminate TLS, and proxy traffic to the application |

Startup order is: database readiness, successful migrations, backend readiness, then Nginx.

Neither MySQL nor the backend publishes ports directly on the host. Nginx publishes ports 80 and 443 on the local loopback address only. The database network is isolated from external networking.

### 3.5. Testing persistent storage

**What does a volume do?** It keeps data beyond the lifetime of a container. A container can be removed and recreated with the same volume, preserving its contents.

**Why are two volumes needed?** The MySQL volume holds database data. The backend storage volume holds uploaded file contents. A file record in the database does not mean the file bytes are stored there.

**Example:** The database contains a document's name, location, and owner, while the storage volume contains its bytes. Both must be preserved for downloads to keep working after deployment.

**What did the test prove?** Replacing containers does not remove data in their attached volumes. This does not protect against volume deletion or disk failure; backups are needed for those cases.

Two volumes were configured separately from development:

| Volume | Contents |
| --- | --- |
| `transcendence-prod_mysql_data` | Database data |
| `transcendence-prod_backend_storage` | Uploaded files under the storage directory |

A temporary database record and test file were created. The MySQL, migration, and backend containers were then recreated. Container IDs changed, but volume names stayed the same, and both the record and file survived. The test data was removed afterward.

This confirms persistence across container replacement. Independent backups are still needed for volume deletion or loss of the machine.

### 3.6. Configuring the Nginx reverse proxy and local TLS

**What does Nginx do?** It provides a single entry point, receives requests, handles HTTPS, and forwards traffic to the backend. The setup uses an existing Nginx image, so a separate Nginx Dockerfile was unnecessary.

**What does `nginx.conf` do?** It defines ports, routing, TLS files, and WebSocket forwarding. The configuration is mounted read-only inside the container using `ro`.

| Item | Role |
| --- | --- |
| Port 80 | Receive HTTP requests and redirect to HTTPS |
| Port 443 | Receive HTTPS and terminate TLS at Nginx |
| `proxy_pass` | Forward the request to `backend:3000` over the Docker network |
| `fullchain.pem` | Present the TLS certificate so the client can verify the endpoint identity |
| `privkey.pem` | Private key used by Nginx during the TLS handshake; it must not be shared or committed to Git |
| `Upgrade` and `Connection` | Allow an HTTP connection to upgrade to WebSocket |
| `client_max_body_size` | Limit request size before forwarding it to the backend |

**Why use a local certificate?** HTTPS is needed while working on localhost. A self-signed certificate provides encryption but is not automatically trusted by the browser. Tests therefore explicitly trusted the local certificate.

**Important:** A `443:80` Compose port mapping does not create TLS. The setup requires `443:443`, `listen 443 ssl`, a certificate, and its private key. After terminating TLS, Nginx can communicate with the backend over internal HTTP as allowed by the subject.

The Nginx configuration was created at:

```text
nginx/nginx.conf
```

It includes:

- HTTP-to-HTTPS redirects using status code 308.
- TLS 1.2 and TLS 1.3 support.
- Proxying to the application's internal port 3000.
- WebSocket upgrade support.
- Forwarded request information and selected security headers.
- An 11 MiB request limit to accommodate a 10 MiB file plus multipart form overhead.

A local self-signed TLS certificate covering localhost and its loopback address was generated under:

```text
nginx/certs/
```

The private key was protected with permissions `600`, and the directory was excluded from Git. The certificate is valid for one year; renewal is currently manual.

**Validation:** Nginx configuration validation passed, the health endpoint worked over HTTPS, and HTTP redirection succeeded. Browsers display a warning unless they trust the local certificate.

### 3.8. Testing recovery after interruption

**What does `restart: unless-stopped` do?** It restarts a container when its process exits unless the container has been intentionally stopped. It does not automatically rerun migrations on every backend restart.

**Why also test a MySQL restart?** A running container is not sufficient: the application must reconnect to the database and handle requests correctly.

**Why use a login request?** The current `/health` endpoint returns a fixed response. A login attempt queries the database to find an account, so it helps verify actual database reconnection.

**Limit:** Docker does not restart a container solely because it becomes unhealthy. The restart policy here reacts to process exit, not just the health-check result.

- The backend process was terminated abruptly to simulate a crash. Docker restarted it automatically.
- MySQL was restarted, and its health check was allowed to pass.
- HTTPS availability and a database-dependent login request were verified afterward.

### 3.10. Preparing and testing backup and restore

**What is a backup?** A separate copy that can be used if data is deleted or damaged. Restore rebuilds the database and files from that copy.

**Why does `backup.sh` temporarily stop the backend?** To prevent a file and its database metadata from changing between their respective backup steps. This provides a consistent snapshot, assuming no other process writes directly to the database during the backup.

| Backup output | Contents or purpose |
| --- | --- |
| `database.sql.gz` | SQL to recreate tables and restore data, generated by `mysqldump` and compressed with gzip |
| `files.tar.gz` | Archive of storage contents, including uploaded files |
| `backend-image.txt` | Backend image ID at backup time, used to match the application version |
| `mysql-image.txt` | MySQL image ID at backup time |
| `SHA256SUMS` | Checksums for checking that files match their recorded contents |

**Understanding these files:** Image ID files do not contain the images themselves. Compression and checksums do not encrypt a backup; its contents remain private data that needs protection.

**What does `restore-test.sh` do?** It creates a new Compose project and new volumes, imports SQL, extracts files, starts services, and checks database access and migration state. It refuses to overwrite existing resources, protecting the original environment.

**Why remove the test data from the source before restore?** To prove that the record and file were recovered from the backup rather than read from the original environment.

**What was still missing on 5 November?** Scheduled backups, retention, an off-machine copy, and a procedure for replacing a damaged environment with a restored one. Scheduling and retention were completed later, as documented below. Backups remain on the same machine, and `restore-test` validates isolated recovery only.

The following tools were created:

| File | Purpose |
| --- | --- |
| `scripts/backup.sh` | Temporarily stop application writes, back up the database and files, calculate checksums, and attempt to start the application again even if backup fails |
| `scripts/restore-test.sh` | Validate a backup and restore it into new isolated containers, refusing existing resources or the production project name |
| `docs/deployment/BACKUP_AND_RESTORE.md` | Document usage, verification, and current limitations |

The backup directory was excluded from Git, and backups were created with restricted permissions.

4. Restore the backup into new isolated volumes.
5. Confirm that the record and file were recovered with identical contents.

## 10. Update on 7 November 2026: Docker log rotation

### Purpose

Services write startup events and errors to stdout and stderr, which Docker collects. These logs help distinguish an Nginx-to-backend connection failure from a problem inside the application, MySQL, or migrations.

Previously, all four services used the json-file driver without explicit size limits. The same configuration was added to each service in `docker-compose.prod.yml`:

```yaml
logging:
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"
```

### How it works

- The json-file logging driver stores container output in files managed by Docker on the host.
- Docker rotates the log when it reaches the configured 10 MB limit.
- It retains up to 3 files per container, including the current file, removing the oldest when needed.
- The approximate allowance is 30 MB per container, not for the entire project. This does not affect database volumes or backup retention.
- Rotation needs no additional cron job or script. It does not collect arbitrary internal files that are not written to stdout or stderr.

### Reading logs

```bash
docker compose -f docker-compose.prod.yml logs --follow --timestamps --tail=100 backend
```

Replace `backend` with `nginx`, `mysql`, or `migrate` as needed. Ctrl+C stops following the logs; it does not stop the container.

### Applying the configuration and its limits

Changing Docker logging settings requires container recreation; a restart is insufficient. The configuration was applied using the same images and volumes and holding the backup lock to avoid overlap. Logs belonging to removed containers are not preserved by this setup and must be exported beforehand if needed.

This implements local log rotation only, not the ELK Major. Centralized logging, archiving, and application log formatting depend on the selected modules and coordination with the backend owner. Backend code was not changed.

**Validation:** All four services were recreated successfully. Their actual Docker settings were verified as json-file with `max-size: 10m` and `max-file: 3`, and their logs remained readable. Image IDs and volume names were unchanged. MySQL and the backend returned to healthy, migrations exited with code 0, and the HTTPS health request passed with certificate verification. No large volume of logs was generated to force size-based rotation; verification covered the actual configuration and service operation.

### Understanding the file deletion issue

An uploaded file has physical contents in storage and a database record describing its name, owner, and location. `FilesService.remove()` first saves `deletedAt`, then attempts to remove the physical file. Marking a record this way is a soft delete.

The current implementation uses:

```ts
await unlink(absolutePath).catch(() => undefined);
```

`unlink` attempts deletion. If it fails, `catch` ignores the error and allows execution to continue. The record can therefore be marked deleted while the physical contents remain in storage. A `FILE_DELETED` activity is then requested and the operation returns successfully. Repeated failures could accumulate files that no longer appear to users but still consume storage. This does not mean all deletions fail.

**Isolated runtime reproduction:** The compiled FilesService from the production image was executed in a separate Node.js process. It used an in-memory repository, stubbed dependent services, and a real temporary file under `/tmp`. Deletion permission was removed from the containing directory, and an actual unlink attempt confirmed `EACCES` when running as `node`, UID 1000.

`remove()` returned successfully, saved `deletedAt` in the test repository, and requested creation of a `FILE_DELETED` activity. The physical file remained, and no service logger methods were called. This tests the compiled service with a real filesystem failure. It is not a full HTTP test or proof that production data currently contains orphaned files.

Directory permissions were restored and the temporary files removed afterward. Production MySQL data and the storage volume were not used, and backend code was neither modified nor restarted. The HTTPS `/health` check returned 200 after the tests.

## 12. Update on 7 November 2026: minimizing sensitive data in Nginx access logs

### The problem

A GitHub OAuth callback passes through Nginx and may include query parameters such as `code` and `state`. The code is a temporary value used to obtain an access token; state helps associate the callback with the OAuth flow initiated by the application.

The default access log format recorded the full request line, potentially including those values. Referer could also contain a URL with sensitive values. The review identified this configuration risk; it did not establish that a real OAuth code had been logged. HTTPS protects data in transit but does not prevent Nginx from logging a decrypted request.

### What changed and what each setting does

The following was added to the `http` block in `nginx/nginx.conf`:

```nginx
log_format app_access '$remote_addr [$time_iso8601] '
                      '"$request_method $uri $server_protocol" '
                      '$status $body_bytes_sent '
                      'request_time=$request_time '
                      'upstream_time=$upstream_response_time';
access_log /dev/stdout app_access;
```

| Setting | Purpose |
| --- | --- |
| `log_format app_access` | Define a named access-log format |
| `$remote_addr` | Address of the connecting peer as seen by Nginx |
| `$time_iso8601` | Request timestamp with timezone information |
| `$request_method` | Request method, such as GET or POST |
| `$uri` | Normalized path without query parameters |
| `$server_protocol` | HTTP protocol version |
| `$status` | Result status code, such as 200 or 401 |
| `$body_bytes_sent` | Response body bytes, excluding response headers |
| `$request_time` | Total request processing time at Nginx, in seconds |
| `$upstream_response_time` | Backend response time; `-` when no upstream is contacted, such as for a redirect |
| `access_log /dev/stdout app_access` | Use this format for HTTP and HTTPS and send output to Docker for the existing log rotation |

The format excludes query parameters, Referer, User-Agent, Authorization, cookies, and request bodies. Paths are still recorded, so secrets must not be placed in path segments.

Example using synthetic values:

```text
Before: GET /github/callback?code=EXAMPLE_CODE&state=EXAMPLE_STATE HTTP/1.1
After:  GET /github/callback HTTP/1.1
```

Full query parameters still reach the backend and remain in HTTP-to-HTTPS redirects. Only logging changed; backend code, proxy_pass, and Compose were not modified.

### Application and validation

`nginx -t` passed before `nginx -s reload` was issued. The container ID and start time stayed the same; no container restart or recreation occurred. A graceful reload applies the new configuration while older workers finish their existing work.

Requests were sent with unique synthetic values in code, state, Referer, User-Agent, Cookie, and Authorization. New logs were then inspected:

- HTTPS `/health` returned 200 with TLS certificate verification.
- HTTP returned 308 and preserved the original query in the Location header.
- An Engine.IO polling handshake through Nginx returned 200. This confirms that the required EIO and transport query values reached the backend; it is not a full WebSocket upgrade or OAuth test.
- The temporary Engine.IO session was closed after verification.
- Access lines retained paths, statuses, and timings without synthetic values or query parameters.
- The backend and MySQL remained healthy, and the migration container remained exited with code 0.

**Limits:** This change applies to new access logs. It does not rewrite or delete old logs, or change Nginx error logs or backend logs. Error logs may include request details during some failures; those failures were not induced during this test. This is not a universal guarantee that every secret is removed from every log.

Configuration follows the [Nginx logging documentation](https://nginx.org/en/docs/http/ngx_http_log_module.html), and application follows the [Nginx reload documentation](https://nginx.org/en/docs/control.html).
